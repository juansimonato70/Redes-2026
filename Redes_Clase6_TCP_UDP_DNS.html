6.1 TCP y UDP

6.1.0 Introducción

TCP (Transmission Control Protocol) y UDP (User Datagram Protocol) son los dos protocolos principales de la capa de transporte (Capa 4 del modelo OSI). Ambos operan sobre IP, pero con filosofías fundamentalmente diferentes en cuanto a confiabilidad y velocidad.

Concepto Fundamental: TCP prioriza la confiabilidad garantizando que todos los datos lleguen correctamente y en orden, mientras que UDP prioriza la velocidad, siendo más rápido pero sin garantías de entrega. La elección entre ambos depende de las necesidades específicas de cada aplicación.

6.1.1 TCP y UDP

Característica TCP UDP
Confiabilidad Garantiza entrega ordenada Sin garantías de entrega
Velocidad Más lento (por las verificaciones) Muy rápido (mínimo overhead)
Conexión Orientado a conexión (3-way handshake) Sin conexión (envía y olvida)
Orden de datos Garantiza orden de llegada Puede llegar desordenado
Control de flujo Sí (evita congestión) No
Detección de errores Sí (retransmite si falla) Sí (descarta paquetes defectuosos)
Encabezado 20-60 bytes 8 bytes
Casos de uso Web, email, FTP, SSH Videollamadas, juegos, DNS

TCP - Transmission Control Protocol

TCP es como enviar una carta certificada: el remitente sabe con certeza que la carta llegó. Es ideal cuando la integridad de los datos es crítica.

  • Three-Way Handshake: Antes de enviar datos, TCP establece una conexión mediante SYN, SYN-ACK, ACK
  • Secuenciación: Cada byte tiene un número de secuencia para garantizar orden
  • Reconocimiento: El receptor confirma la recepción de datos
  • Retransmisión: Si no hay confirmación, los datos se reenvían automáticamente
  • Control de congestión: Ajusta automáticamente la velocidad de envío

UDP - User Datagram Protocol

UDP es como enviar un postal: rápido, pero sin garantía de llegada. Ideal cuando la velocidad es más importante que la confiabilidad.

  • Sin conexión: No establece conexión previa, envía datos directamente
  • Datagramas independientes: Cada paquete es independiente
  • Bajo overhead: Mínimo encabezado (8 bytes vs 20+ de TCP)
  • Ideal para streaming: Mejor para aplicaciones en tiempo real
  • Aplicaciones tolerantes: Se usa cuando perder algunos paquetes es aceptable
Comparación Práctica:

Escenario 1: Descarga de archivo (Usar TCP)
• Necesitas que TODOS los bytes del archivo lleguen correctamente
• Un archivo corrupto es inútil
• La velocidad es secundaria a la confiabilidad
• Si se pierde un paquete, se retransmite automáticamente

Escenario 2: Videollamada (Usar UDP)
• Perder 1-2 paquetes de video cada segundo es tolerable
• La latencia baja es crítica (debe ser en tiempo real)
• TCP sería demasiado lento con retransmisiones
• Si se pierde un frame, simplemente continuamos

Resultado en experiencia de usuario:
• TCP: Archivo perfecto pero descarga más lenta
• UDP: Videollamada fluida aunque ocasionalmente pixelada

6.1.2 Números de Puerto

Los números de puerto son identificadores lógicos de 16 bits (0-65535) que permiten que múltiples aplicaciones compartan la misma dirección IP en un dispositivo. Un puerto es como un número de apartamento: múltiples servicios pueden coexistir en la misma dirección IP pero en diferentes puertos.

Todo el tráfico de los distintos puertos (80, 443, 22, 25...) entra y sale por la misma interfaz de red física

Rango de Puertos

  • Puertos conocidos (Well-Known): 0-1023 (reservados para servicios del sistema)
  • Puertos registrados: 1024-49151 (aplicaciones comerciales registradas)
  • Puertos dinámicos: 49152-65535 (clientes y aplicaciones temporales)
Puerto Protocolo Servicio Descripción
20, 21 TCP FTP Transferencia de archivos (20=datos, 21=control)
22 TCP SSH Acceso remoto seguro
23 TCP Telnet Acceso remoto sin encripción (obsoleto)
25 TCP SMTP Envío de correo electrónico
53 TCP/UDP DNS Resolución de nombres de dominio
80 TCP HTTP Web sin encripción
110 TCP POP3 Recepción de correo electrónico
143 TCP IMAP Recepción de correo (más moderno que POP3)
443 TCP HTTPS Web encriptado (seguro)
3306 TCP MySQL Base de datos
3389 TCP/UDP RDP Escritorio remoto Windows
Detalle Importante: Una conexión de red se identifica únicamente por una tupla de 5 elementos: (IP origen, puerto origen, IP destino, puerto destino, protocolo). Esto significa que el mismo puerto en direcciones IP diferentes representa conexiones completamente distintas.

6.2 Servicios de la Capa de Aplicación

6.2.0 Introducción

La capa de aplicación (Capa 7 del modelo OSI) es donde interactúan los usuarios y las aplicaciones. Los servicios aquí son protocolos que definen cómo las aplicaciones se comunican entre sí y con los usuarios. Sin estos protocolos estandarizados, cada aplicación tendría que inventar su propio sistema de comunicación.

6.2.1 La Relación de Cliente-Servidor

La mayoría de los servicios de red modernos siguen la arquitectura cliente-servidor. Este modelo define roles claros y específicos para cada participante en la comunicación.

Modelo Cliente-Servidor

  • Cliente: Inicia la conexión, realiza solicitudes, espera respuestas
  • Servidor: Escucha en un puerto específico, responde a solicitudes de múltiples clientes
  • Asimetría: Cliente y servidor juegan roles distintos, no intercambiables
  • Escalabilidad: Un servidor puede atender a miles de clientes simultáneamente
💻

Cliente 1

Solicita datos
💻

Cliente 2

Solicita datos
→
🖥️

Servidor

Responde a todos

Un servidor físico real: atiende simultáneamente las solicitudes de múltiples clientes

6.2.2 Servicios de Aplicaciones de Red

Existen numerosos servicios de aplicación que conforman Internet. Cada uno resuelve un problema específico de comunicación.

Servicios Principales:

  • DNS: Traduce nombres de dominio a direcciones IP
  • HTTP/HTTPS: Protocolo de transferencia hipertexto para la web
  • FTP: Transferencia de archivos
  • SMTP/POP3/IMAP: Servicios de correo electrónico
  • SSH/Telnet: Acceso remoto a máquinas
  • DHCP: Asignación automática de direcciones IP
  • SNMP: Monitoreo y gestión de dispositivos de red
  • NTP: Sincronización de reloj en red

6.2.3 Sistema de Nombres de Dominio (DNS)

El DNS (Domain Name System) es uno de los servicios más críticos de Internet. Permite que los usuarios recuerden nombres fáciles como "google.com" en lugar de direcciones IP numéricas como "142.250.185.46".

¿Por qué es importante DNS?

  • Las direcciones IP son difíciles de recordar para humanos
  • Las empresas pueden cambiar su dirección IP sin cambiar su nombre de dominio
  • Permite distribuir el tráfico entre múltiples servidores (load balancing)
  • Es la base de toda la navegación web moderna
Proceso de Resolución DNS:

Paso 1 - Usuario solicita:
Usuario tipea en navegador: https://www.ejemplo.com

Paso 2 - Consulta DNS local:
El navegador consulta la caché local o el resolver DNS del ISP

Paso 3 - Consulta al servidor raíz (si no está en caché):
Si no está en caché, se consulta el servidor raíz: "¿Dónde está ejemplo.com?"

Paso 4 - Respuesta del TLD (Top Level Domain):
Servidor raíz responde: "Pregunta al servidor .com"

Paso 5 - Respuesta del servidor autoritativo:
Servidor .com responde: "La IP de ejemplo.com es 93.184.216.34"

Paso 6 - Navegador conecta:
Con la IP, el navegador establece conexión TCP hacia 93.184.216.34:443

Tiempo total: Típicamente 50-200ms (casi instantáneo para el usuario)
# Consultar DNS desde Windows
nslookup google.com

# Consultar DNS desde Linux
dig google.com
nslookup google.com

# Ver caché DNS
ipconfig /displaydns (Windows)
systemd-resolve --statistics (Linux)

6.2.4 Clientes y Servidores Web

La web se basa en la arquitectura cliente-servidor usando el protocolo HTTP (HyperText Transfer Protocol) y su versión encriptada HTTPS.

HTTP - HyperText Transfer Protocol

  • Sin estado (Stateless): Cada solicitud es independiente, el servidor no mantiene contexto
  • Métodos principales:
    • GET: Solicita un recurso
    • POST: Envía datos al servidor
    • PUT: Reemplaza un recurso completo
    • DELETE: Elimina un recurso
  • Códigos de estado:
    • 2xx: Éxito (200 OK, 201 Created)
    • 3xx: Redirección (301 Moved, 304 Not Modified)
    • 4xx: Error del cliente (404 Not Found, 403 Forbidden)
    • 5xx: Error del servidor (500 Internal Error, 503 Unavailable)

HTTPS - HTTP Seguro

HTTPS es HTTP encriptado usando SSL/TLS. Protege la comunicación del navegador con el servidor.

  • Encriptación: Los datos viajan encriptados
  • Autenticación: Verifica que el servidor es genuino (certificados)
  • Integridad: Detecta si alguien modificó los datos
  • Puerto 443: Se ejecuta en puerto 443 en lugar de 80
Ciclo de vida de una solicitud HTTP:

1. Cliente (Navegador) solicita:
GET /index.html HTTP/1.1
Host: www.ejemplo.com
User-Agent: Mozilla/5.0

2. Servidor responde:
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1234

<html>...contenido de la página...</html>

3. Navegador renderiza:
Interpreta HTML, CSS, JavaScript y muestra la página

6.2.5 Clientes y Servidores FTP

FTP (File Transfer Protocol) es un protocolo especializado para transferir archivos entre computadoras. Aunque fue revolucionario, está siendo reemplazado por alternativas más seguras como SFTP (SSH File Transfer Protocol).

Características de FTP

  • Dos conexiones: Puerto 21 para comandos, puerto 20 para datos
  • Modos de transferencia:
    • Activo: Servidor inicia conexión de datos hacia cliente
    • Pasivo: Cliente inicia ambas conexiones (recomendado)
  • Sin encripción: Las credenciales se envían en texto plano (¡peligroso!)
  • Velocidad: Optimizado para transferencias de grandes archivos
  • Tipos de datos: ASCII y BINARY (binario)
Advertencia de Seguridad: FTP es inseguro. Nunca use FTP en redes públicas o sin protección. Use SFTP (SSH) o FTPS (FTP sobre SSL) en su lugar. FTP todavía se usa en entornos corporativos internos, pero está obsoleto para la mayoría de aplicaciones.
# Conectar a servidor FTP desde línea de comandos
ftp ftp.ejemplo.com

# Comandos FTP comunes una vez conectado
ls (listar archivos)
cd directorio (cambiar directorio)
get archivo (descargar archivo)
put archivo (subir archivo)
mget *.txt (descargar múltiples archivos)
bye (desconectar)

6.2.6 Terminales Virtuales

Las terminales virtuales permiten acceder a máquinas remotas como si estuvieras sentado frente a ellas. Los protocolos más comunes son Telnet (antiguo e inseguro) y SSH (moderno y seguro).

Telnet - Terminal Network (Obsoleto)

  • Puerto: 23
  • Sin encripción: Todo se envía en texto plano
  • Credenciales comprometidas: Cualquiera en la red puede interceptar usuario y contraseña
  • Estado: Prácticamente obsoleto, solo usado en ambientes muy antiguos
  • Nota: Todavía se usa para probar conectividad en puertos específicos

SSH - Secure Shell (Recomendado)

  • Puerto: 22
  • Encriptación completa: Todos los datos están encriptados
  • Autenticación segura: Usuario/contraseña o claves públicas
  • Túneles seguros: Permite tunelizar otros servicios a través de SSH
  • Standard moderno: Único protocolo de acceso remoto seguro recomendado
# Conectar con SSH
ssh usuario@servidor.com
ssh -p 2222 usuario@servidor.com (puerto personalizado)

# Generar clave SSH
ssh-keygen -t rsa -b 4096

# Probar conectividad con Telnet (para debugging)
telnet ejemplo.com 80

6.2.7 Correo Electrónico y Mensajería

El correo electrónico es uno de los servicios más antiguos y confiables de Internet. Utiliza varios protocolos diferentes para enviar, recibir y almacenar mensajes.

SMTP - Simple Mail Transfer Protocol

  • Propósito: Enviar correos electrónicos
  • Puerto: 25 (no encriptado), 587 (TLS), 465 (SSL)
  • Dirección: Siempre hacia el servidor de correo saliente
  • Proceso: Cliente conecta, autentica, envía mensaje
  • Ruta: Tu cliente → SMTP servidor → SMTP servidor destino

POP3 - Post Office Protocol v3

  • Propósito: Recibir y descargar correos
  • Puerto: 110 (no encriptado), 995 (SSL)
  • Modelo: Descarga mensajes a cliente local, generalmente borra del servidor
  • Uso: Ideal si tienes una sola máquina para acceder al correo
  • Limitación: No sincroniza entre dispositivos

IMAP - Internet Message Access Protocol

  • Propósito: Acceder al correo sin descargar
  • Puerto: 143 (no encriptado), 993 (SSL)
  • Modelo: Conecta al servidor, lee emails remotamente, mantiene sincronización
  • Uso: Ideal para múltiples dispositivos (teléfono, tablet, PC)
  • Ventaja: Sincronización automática de estados (leído, respondido, etc.)
Flujo de Correo Electrónico:

Scenario: Juan (juan@empresa1.com) envía a María (maria@empresa2.com)

1. Composición y Envío:
Juan escribe correo en su cliente de correo
Cliente conecta a smtp.empresa1.com:587 (SMTP seguro)

2. Autenticación:
Cliente autentica con usuario y contraseña

3. Transmisión SMTP:
Servidor SMTP de empresa1 recibe el mensaje
Consulta DNS para encontrar servidor SMTP de empresa2.com
Conecta a smtp.empresa2.com y envía el correo

4. Almacenamiento:
Servidor de empresa2 almacena el correo en el buzón de María

5. Recepción:
María conecta con su cliente de correo
Cliente conecta a imap.empresa2.com:993
Autentica y descarga lista de correos
María ve el correo de Juan

Protocolos utilizados:
• SMTP: Envío (empresa1 → empresa2)
• IMAP: Recepción (María accede al servidor)
# Configuración típica de cliente de correo
Servidor SMTP: smtp.correo.com
Puerto SMTP: 587 (con STARTTLS)
Usuario SMTP: tu@correo.com

Servidor IMAP: imap.correo.com
Puerto IMAP: 993 (SSL)
Usuario IMAP: tu@correo.com
