12.1 Soporte de Red

12.1.0 Introducción

El soporte de red es un componente crítico de las operaciones de TI en cualquier organización. Va más allá de simplemente "arreglar cosas rotas" - implica mantener la infraestructura de red funcionando de manera óptima, documentar configuraciones, gestionar cambios, y proporcionar asistencia efectiva a los usuarios.

Objetivos del Soporte de Red

  • Disponibilidad: Mantener la red funcionando con mínimo tiempo de inactividad
  • Rendimiento: Asegurar que la red opere a velocidades óptimas
  • Seguridad: Proteger la infraestructura y los datos
  • Escalabilidad: Permitir crecimiento sin degradación
  • Satisfacción del usuario: Resolver problemas rápida y efectivamente
  • Cumplimiento: Adherirse a políticas y regulaciones

Roles Comunes en Soporte de Red

  • Network Administrator (Administrador de Red):
    • Configura y mantiene equipos de red
    • Gestiona VLANs, routing, seguridad
    • Aplica actualizaciones y parches
  • Help Desk / Service Desk:
    • Primera línea de contacto para usuarios
    • Resuelve problemas básicos
    • Escala problemas complejos
  • Network Engineer (Ingeniero de Redes):
    • Diseña arquitecturas de red
    • Planifica expansiones
    • Resuelve problemas complejos
  • NOC (Network Operations Center) Technician:
    • Monitorea la red 24/7
    • Identifica y responde a alertas
    • Gestiona incidentes

Soporte Reactivo vs Proactivo:

Soporte Reactivo:
• Esperar a que ocurran problemas
• Responder a tickets de usuarios
• "Apagar incendios"
• Común pero no ideal

Soporte Proactivo (MEJOR):
• Monitorear constantemente
• Identificar problemas antes de que afecten usuarios
• Mantenimiento preventivo regular
• Análisis de tendencias
• Actualizaciones planificadas

El objetivo es ser 80% proactivo, 20% reactivo.

12.1.1 Metodologías de Diagnóstico y Solución de Problemas

Una metodología estructurada es fundamental para resolver problemas de red de manera eficiente y consistente. Diferentes metodologías son apropiadas para diferentes situaciones.

Metodologías Principales

1. Modelo OSI de 7 Capas - Enfoque Bottom-Up

Estrategia: Comenzar en Capa 1 (Física) y avanzar hacia arriba

Cuándo usar: Cuando sospechas problemas de hardware o no tienes idea de dónde está el problema

Secuencia de verificación:

  1. Capa 1 - Física: Cables, conectores, LEDs, energía
  2. Capa 2 - Enlace: Switches, VLANs, tabla MAC, ARP
  3. Capa 3 - Red: IPs, máscaras, gateway, routing
  4. Capa 4 - Transporte: TCP/UDP, puertos, firewalls
  5. Capa 5-7 - Aplicación: DNS, DHCP, servicios específicos

Ventajas:

  • Metódico y completo
  • No se saltan pasos
  • Encuentra problemas de base primero

Desventajas:

  • Puede ser lento si el problema está en capas superiores
  • Requiere acceso físico inicial

2. Enfoque Top-Down

Estrategia: Comenzar en Capa 7 (Aplicación) y bajar hacia Capa 1

Cuándo usar: Cuando el problema está relacionado con una aplicación específica

Secuencia de verificación:

  1. Aplicación: ¿Funciona la app? ¿Errores específicos?
  2. DNS: ¿Resuelve nombres correctamente?
  3. Conectividad TCP/IP: ¿Puertos abiertos?
  4. Routing: ¿Rutas correctas?
  5. Switching: ¿VLAN correcta?
  6. Física: ¿Cables conectados?

Ventajas:

  • Rápido para problemas de aplicación/configuración
  • Se enfoca en lo que el usuario realmente ve

Desventajas:

  • Puede pasar por alto problemas físicos obvios
  • Menos sistemático

3. Divide and Conquer (Dividir y Conquistar)

Estrategia: Empezar en una capa media (usualmente Capa 3) y ajustar según resultados

Cuándo usar: Cuando tienes experiencia y quieres ser eficiente

Proceso:

  1. Probar conectividad IP básica (ping)
  2. Si falla: Bajar a capas inferiores (física, enlace)
  3. Si funciona: Subir a capas superiores (transporte, aplicación)

Ejemplo práctico:

  • Empezar: ping 8.8.8.8
  • Si falla → revisar IP local, gateway, cables
  • Si funciona → revisar DNS, aplicación específica

Ventajas:

  • Más rápido en promedio
  • Reduce pasos innecesarios

Desventajas:

  • Requiere experiencia para elegir bien el punto de inicio
  • Puede requerir varias iteraciones

4. Follow the Path (Seguir la Ruta)

Estrategia: Seguir físicamente el camino de los datos desde origen hasta destino

Cuándo usar: Para entrenar nuevos técnicos o en redes pequeñas/simples

Proceso:

  1. PC del usuario → verificar
  2. Cable del PC → verificar
  3. Puerto del switch → verificar
  4. Switch → verificar
  5. Router → verificar
  6. Conexión WAN → verificar
  7. Internet → verificar

Ventajas:

  • Muy intuitivo y fácil de entender
  • Bueno para documentar la topología

Desventajas:

  • Lento en redes grandes
  • Puede perderse en topologías complejas

5. Swap Components (Intercambiar Componentes)

Estrategia: Reemplazar componentes sospechosos con componentes conocidos como funcionales

Cuándo usar: Cuando sospechas hardware defectuoso

Proceso:

  1. Identificar componente sospechoso (cable, NIC, puerto)
  2. Reemplazar con componente funcional conocido
  3. Probar si el problema se resuelve
  4. Si se resuelve → componente original estaba defectuoso
  5. Si persiste → problema está en otra parte

Ejemplos:

  • Cambiar cable de red por uno nuevo
  • Conectar dispositivo a otro puerto del switch
  • Probar con otro adaptador de red

Ventajas:

  • Muy efectivo para problemas de hardware
  • Rápido si tienes repuestos disponibles

Desventajas:

  • Requiere tener componentes de repuesto
  • No funciona para problemas de configuración

6. Spot the Differences (Comparar Configuraciones)

Estrategia: Comparar configuración actual vs configuración funcional conocida

Cuándo usar: Cuando algo "dejó de funcionar" después de cambios

Proceso:

  1. Obtener configuración actual
  2. Comparar con backup/baseline funcional
  3. Identificar diferencias
  4. Evaluar cuál diferencia causó el problema
  5. Revertir o corregir el cambio problemático

Herramientas útiles:

  • Sistemas de control de versiones (Git)
  • Herramientas de diff (WinMerge, Beyond Compare)
  • Backups automatizados de configuraciones

Ventajas:

  • Muy efectivo para cambios recientes
  • Identifica rápidamente la causa

Desventajas:

  • Requiere documentación/backups previos
  • No funciona si no hubo cambios documentados
Ejemplo: Elegir la Metodología Correcta

Escenario 1: "Internet no funciona en toda la oficina"
• Metodología recomendada: Follow the Path
• Por qué: Afecta a todos, probablemente problema central
• Pasos: Router → Módem → ISP

Escenario 2: "No puedo acceder a la base de datos"
• Metodología recomendada: Top-Down
• Por qué: Problema específico de aplicación
• Pasos: App → Servicio DB → Red → Servidor

Escenario 3: "Nueva PC no se conecta a la red"
• Metodología recomendada: Bottom-Up
• Por qué: Dispositivo nuevo, posible problema físico
• Pasos: Cable → Puerto → IP → DNS

Escenario 4: "Red lenta desde ayer"
• Metodología recomendada: Spot the Differences
• Por qué: Funcionaba antes, algo cambió
• Pasos: Revisar cambios recientes

Escenario 5: "Este cable parece sospechoso"
• Metodología recomendada: Swap Components
• Por qué: Sospecha específica de hardware
• Pasos: Cambiar cable y probar
Mejores Prácticas de Diagnóstico:

1. Cambiar una variable a la vez
• No hacer múltiples cambios simultáneos
• Si haces 3 cambios y funciona, no sabes cuál lo arregló

2. Documentar cada paso
• Qué probaste, qué resultado obtuviste
• Útil si necesitas revertir
• Ayuda a otros si necesitas escalar

3. Usar herramientas consistentemente
• ping, traceroute, nslookup siempre en ese orden
• Crea un método reproducible

4. Conocer la línea base (baseline)
• Saber cómo se ve "normal"
• Facilita detectar anomalías

5. Eliminar variables
• Aislar el problema
• "¿Funciona con cable? → entonces no es WiFi"

6. Buscar patrones
• ¿Afecta solo a Windows? → problema de SO
• ¿Solo de 9-11 AM? → problema de carga/ancho de banda
• ¿Solo cierto edificio? → problema local

12.1.2 Documentación de Red

La documentación de red es uno de los activos más valiosos de un departamento de TI. Una red bien documentada es más fácil de mantener, solucionar problemas, y expandir. La falta de documentación puede resultar en tiempo perdido, errores costosos, y dependencia excesiva de personas específicas.

Tipos de Documentación de Red

1. Diagramas de Red

Representaciones visuales de la topología y componentes de la red

Tipos principales:

  • Diagrama Físico (Physical Topology):
    • Ubicación física de dispositivos
    • Racks, salas de equipos, edificios
    • Tipo de cables y longitudes
    • Rutas de cableado
  • Diagrama Lógico (Logical Topology):
    • Cómo fluyen los datos
    • Direccionamiento IP y subredes
    • VLANs y segmentación
    • Protocolos de routing
  • Diagrama de Cableado (Wiring Diagram):
    • Números de puertos
    • Paneles de parcheo
    • Etiquetas de cables

Herramientas para crear diagramas:

  • Microsoft Visio: Estándar de la industria, plantillas de red
  • Lucidchart: Basado en web, colaborativo
  • Draw.io (diagrams.net): Gratis, open source
  • Cisco Packet Tracer: Específico para Cisco, con simulación
  • NetBrain: Documentación automatizada

2. Inventario de Equipos

Lista completa de todos los dispositivos de red

Información a incluir:

  • Información básica:
    • Nombre del dispositivo (hostname)
    • Tipo (router, switch, firewall, AP)
    • Fabricante y modelo
    • Número de serie
  • Ubicación:
    • Edificio, piso, sala
    • Rack y unidad (U)
    • GPS (para sitios remotos)
  • Información técnica:
    • Versión de IOS/firmware
    • RAM, Flash
    • Número de puertos
    • Módulos instalados
  • Información administrativa:
    • Fecha de compra
    • Fecha de instalación
    • Proveedor
    • Contrato de soporte/garantía
    • EOL (End of Life) date
    • Responsable/dueño

Formato de inventario:

  • Hoja de cálculo (Excel/Google Sheets) - simple
  • Sistema CMDB (Configuration Management Database)
  • Sistema DCIM (Data Center Infrastructure Management)
  • Herramientas de descubrimiento automatizado (Spiceworks, Lansweeper)

S/N: FDO2345ABC12
Ubicación: Edificio Principal, Piso 3, Rack A, U10-U12
IOS: 17.3.4
RAM: 8 GB
Puertos: 48x Gigabit PoE+, 4x 10G SFP+
IP Gestión: 192.168.1.10

Instalación: 20/03/2021

Notas: Switch core principal, crítico para operaciones

3. Esquema de Direccionamiento IP (IP Addressing Scheme)

Plan detallado de cómo se asignan las direcciones IP en la red

Información a documentar:

  • Subredes:
    • Rango de cada subred
    • Propósito (usuarios, servidores, impresoras, gestión, WiFi)
    • VLAN asociada
    • Gateway
  • Asignaciones estáticas:
    • Servidores
    • Dispositivos de red
    • Impresoras
    • Cámaras IP
  • Rangos DHCP:
    • Inicio y fin del pool
    • Reservas DHCP
    • Lease time
Ejemplo de Esquema de Direccionamiento:

Oficina Principal - 192.168.0.0/16

Subred de Gestión: 192.168.1.0/24
• Propósito: Gestión de dispositivos de red
• VLAN: 1 (nativa)
• Gateway: 192.168.1.1
• Asignaciones:
  - 192.168.1.1-10: Routers
  - 192.168.1.11-50: Switches
  - 192.168.1.51-100: Access Points
  - 192.168.1.101-150: Firewalls/otros

Subred de Usuarios: 192.168.10.0/24
• Propósito: PCs de usuarios
• VLAN: 10
• Gateway: 192.168.10.1
• DHCP Pool: 192.168.10.100-254
• Estáticas: 192.168.10.1-99 (reservadas)

Subred de Servidores: 192.168.20.0/24
• Propósito: Servidores internos
• VLAN: 20
• Gateway: 192.168.20.1
• Todas estáticas:
  - 192.168.20.10: DC01 (Domain Controller)
  - 192.168.20.11: DC02 (Domain Controller secundario)
  - 192.168.20.20: FILE01 (File Server)
  - 192.168.20.30: WEB01 (Web Server interno)
  - 192.168.20.40: DB01 (Database Server)

Subred WiFi Guest: 192.168.100.0/24
• Propósito: Invitados WiFi
• VLAN: 100
• Gateway: 192.168.100.1
• DHCP Pool: 192.168.100.10-254
• Aislada de red interna

4. Archivos de Configuración

Backups de configuraciones de todos los dispositivos de red

Mejores prácticas:

  • Backups automáticos regulares:
    • Diarios para dispositivos críticos
    • Semanales para otros
    • Usar herramientas como RANCID, Oxidized
  • Control de versiones:
    • Git para rastrear cambios
    • Comentarios descriptivos de cada cambio
    • Quién, cuándo, por qué
  • Almacenamiento seguro:
    • Servidor de backups dedicado
    • Cifrado para configs con credenciales
    • Backups off-site / en la nube
  • Nomenclatura consistente:
    • Formato: hostname_fecha_hora.cfg
    • Ejemplo: SW-Core-01_2024-12-07_14-30.cfg

5. Políticas y Procedimientos

Documentos que guían las operaciones de red

Documentos típicos:

  • Change Management Policy: Cómo se aprueban e implementan cambios
  • Password Policy: Requisitos de contraseñas, rotación
  • Access Control Policy: Quién tiene acceso a qué
  • Incident Response Plan: Qué hacer en emergencias
  • Disaster Recovery Plan: Cómo recuperarse de desastres
  • Standard Operating Procedures (SOPs):
    • Cómo agregar un nuevo usuario
    • Cómo configurar un nuevo switch
    • Cómo responder a un incidente de seguridad

6. Base de Conocimiento (Knowledge Base)

Repositorio de soluciones a problemas comunes

Contenido típico:

  • Artículos de troubleshooting: "Cómo resolver X problema"
  • FAQs: Preguntas frecuentes de usuarios
  • Guías paso a paso: Configuraciones comunes
  • Lecciones aprendidas: Post-mortems de incidentes
  • Tips y trucos: Mejores prácticas

Plataformas:

  • Confluence, SharePoint, MediaWiki
  • Sistemas de ticketing con KB integrada
  • Documentación interna en Markdown + Git

7. Información de Contactos

Lista de contactos importantes

Incluir:

  • Internos:
    • Equipo de red (con especialidades)
    • Equipo de seguridad
    • Gerentes de TI
    • Personal on-call
  • Externos:
    • ISPs (números de soporte, cuentas)
    • Proveedores de equipos
    • Contratistas
    • Soporte técnico de fabricantes
  • Emergencias:
    • Escalamiento crítico 24/7
    • Contactos de gerencia
Mejores Prácticas de Documentación:

1. Mantenerla actualizada
• Actualizar CADA vez que haces un cambio
• "Lo haré después" = nunca se hace
• Incorporar en el proceso de cambios

2. Hacerla accesible
• Almacenar en ubicación central conocida
• Todos los técnicos deben tener acceso
• Pero controlar acceso (no todos editan)

3. Usar nomenclatura consistente
• Convención de nombres clara
• Prefijos/sufijos consistentes
• Ejemplo: SW-Piso2-01, SW-Piso2-02, etc.

4. Incluir metadatos
• Fecha de creación/modificación
• Autor/responsable
• Versión

5. Revisar periódicamente
• Auditoría trimestral/semestral
• Eliminar documentación obsoleta
• Actualizar cambios no documentados

6. Hacer backups de la documentación
• La documentación también necesita backup
• Almacenar fuera de la red de producción
• Tener copias impresas de diagramas críticos

7. Documentar el "por qué"
• No solo "qué" está configurado
• Sino "por qué" se configuró así
• Ejemplo: "VLAN 10 aislada porque usuarios guest"
Sin Documentación:
• "¿Por qué este switch tiene esta config rara?"
• "¿Cuál es la contraseña del router del 3er piso?"
• "¿Qué pasa si el administrador de red renuncia?"
• "¿Podemos agregar 50 PCs más en esta red?"
• Pérdida de tiempo buscando información
• Riesgo de romper algo sin saber por qué estaba así

Con Buena Documentación:
• Respuestas rápidas a preguntas
• Onboarding rápido de nuevos técnicos
• Troubleshooting más eficiente
• Planificación de cambios informada
• Menor dependencia de individuos específicos
• Cumplimiento de auditorías más fácil

Checklist de Documentación Mínima Necesaria

  • Diagrama de topología física actualizado
  • Diagrama de topología lógica actualizado
  • Inventario completo de equipos
  • Esquema de direccionamiento IP
  • Lista de VLANs y su propósito
  • Configuraciones de backups de todos los dispositivos
  • Credenciales de acceso (en ubicación segura)
  • Contactos de soporte (ISP, proveedores)
  • Procedimientos de cambios
  • Procedimientos de respaldo/recuperación
  • Base de conocimiento con problemas comunes
  • Log de cambios (change log)

    • 12.1.3 Mesas de Ayuda

    La Mesa de Ayuda (Help Desk o Service Desk) es el punto de contacto principal entre los usuarios y el equipo de TI. Su efectividad impacta directamente en la productividad de la organización y la satisfacción de los usuarios.

    Modelo de Niveles de Soporte (Tiered Support)

    Tier 1 - Help Desk (Primera Línea)

    Rol: Primer punto de contacto, resolución de problemas básicos

    Responsabilidades:

    • Recibir y documentar solicitudes de usuarios
    • Resolver problemas comunes y conocidos
    • Resetear contraseñas
    • Guiar usuarios en procedimientos básicos
    • Escalar problemas complejos a Tier 2
    • Mantener base de conocimiento actualizada

    Habilidades requeridas:

    • Excelentes habilidades de comunicación
    • Paciencia y empatía
    • Conocimientos básicos de IT
    • Capacidad de seguir procedimientos

    Métricas típicas:

    • First Call Resolution (FCR): 60-70%
    • Tiempo de respuesta: < 5 minutos
    • Tiempo de resolución: < 30 minutos para problemas comunes

    Tier 2 - Technical Support (Soporte Técnico)

    Rol: Problemas más complejos que requieren conocimiento técnico profundo

    Responsabilidades:

    • Resolver problemas escalados de Tier 1
    • Troubleshooting avanzado de red
    • Configuración de equipos de red
    • Gestión de problemas de conectividad
    • Análisis de logs y tráfico de red
    • Implementar cambios menores

    Habilidades requeridas:

    • Conocimiento profundo de protocolos de red
    • Experiencia con equipos Cisco/otros fabricantes
    • Habilidades de análisis y diagnóstico
    • Certificaciones (CCNA, Network+, etc.)

    Métricas típicas:

    • Tiempo de resolución: 2-4 horas
    • Tasa de escalamiento a Tier 3: < 10%

    Tier 3 - Network Engineers/Arquitectos

    Rol: Expertos, problemas críticos y complejos

    Responsabilidades:

    • Problemas críticos que afectan toda la red
    • Diseño e implementación de soluciones
    • Cambios mayores en infraestructura
    • Planificación de capacidad
    • Trabajo con proveedores (TAC de Cisco, etc.)
    • Root Cause Analysis (RCA) de incidentes mayores

    Habilidades requeridas:

    • Experticia avanzada en redes
    • Experiencia con arquitecturas complejas
    • Certificaciones avanzadas (CCNP, CCIE)
    • Capacidad de diseño y planificación

    Sistema de Ticketing

    Un sistema de tickets es fundamental para gestionar solicitudes de soporte de manera organizada y rastreable.

    Elementos de un ticket:

    • Número de ticket: Identificador único (ej: INC0012345)
    • Fecha/hora de creación
    • Solicitante: Nombre, email, departamento, teléfono
    • Categoría: Red, Hardware, Software, Acceso, etc.
    • Prioridad: Crítica, Alta, Media, Baja
    • Estado: Nuevo, En progreso, Pendiente, Resuelto, Cerrado
    • Asignado a: Técnico responsable
    • Descripción del problema: Detallada
    • Notas de trabajo: Log de acciones tomadas
    • Resolución: Solución aplicada
    • SLA (Service Level Agreement): Tiempo límite de respuesta/resolución

    Ciclo de Vida de un Ticket

    1. Creación:
      • Usuario reporta problema (teléfono, email, portal web, chat)
      • Sistema crea ticket automático
      • Se asigna número único
    2. Triaje y Asignación:
      • Determinar prioridad
      • Asignar a técnico o equipo apropiado
      • Iniciar contador de SLA
    3. Trabajo en Progreso:
      • Técnico investiga y documenta pasos
      • Puede cambiar prioridad si necesario
      • Puede escalar a nivel superior
      • Actualiza al usuario regularmente
    4. Resolución:
      • Se implementa solución
      • Se documenta qué se hizo
      • Se marca como "Resuelto"
      • Usuario es notificado
    5. Cierre:
      • Usuario confirma que el problema está resuelto
      • O se cierra automáticamente después de X días sin respuesta
      • Encuesta de satisfacción (opcional)
      • Ticket archivado

    Niveles de Prioridad

    Prioridad Impacto Tiempo de Respuesta Tiempo de Resolución Ejemplos
    P1 - Crítica Toda la red/sistema caído 15 minutos 4 horas Internet caído, core switch down, ransomware
    P2 - Alta Departamento/servicio afectado 1 hora 8 horas Switch de piso caído, VPN inaccesible
    P3 - Media Usuarios individuales afectados 4 horas 24 horas PC sin conectividad, impresora no funciona
    P4 - Baja Inconvenientes menores 8 horas 5 días Solicitud de cambio, pregunta general

    Mejores Prácticas de Help Desk

    1. Primera Interacción con el Usuario:

    • Saludar profesionalmente
    • Presentarse y proporcionar número de ticket
    • Escuchar activamente sin interrumpir
    • Mostrar empatía: "Entiendo que esto debe ser frustrante"

    2. Recopilación de Información:

    • Hacer preguntas abiertas primero: "¿Puede describirme el problema?"
    • Luego preguntas específicas: "¿Cuándo comenzó exactamente?"
    • Verificar información básica: nombre, ubicación, departamento
    • Reproducir el problema si es posible

    3. Durante la Resolución:

    • Explicar qué estás haciendo (sin jerga técnica excesiva)
    • Mantener al usuario informado del progreso
    • Si tomará tiempo, dar estimación realista
    • No dejar al usuario esperando sin comunicación

    4. Documentación del Ticket:

    • Escribir notas claras y detalladas
    • Usar formato consistente
    • Incluir pasos de troubleshooting realizados
    • Documentar solución exacta aplicada
    • Pensar: "Si leo esto en 6 meses, ¿entenderé qué pasó?"

    5. Cierre del Ticket:

    • Confirmar con el usuario que el problema está resuelto
    • Preguntar si hay algo más que puedas ayudar
    • Explicar cómo prevenir el problema en el futuro
    • Agradecer por su paciencia

    12.1.4 Solucionar Problemas de Conectividad de Dispositivos Finales

    Los dispositivos finales (PCs, laptops, tablets, smartphones) son donde los usuarios experimentan los problemas. La mayoría de los tickets de help desk involucran estos dispositivos.

    La revisión física del cable y la NIC es siempre el primer paso ante un "sin conectividad"

    Problemas Comunes de Dispositivos Finales

    Problema 1: "No Hay Conectividad de Red"

    Síntomas: Icono de red con X roja, "Sin acceso a red", cable desconectado

    Pasos de troubleshooting:

    1. Verificar físico (si es cableado):
      • Cable conectado en ambos extremos
      • LED de link encendido en NIC y switch
      • Probar con otro cable conocido funcional
      • Probar conectando a otro puerto del switch
    2. Verificar WiFi (si es inalámbrico):
      • WiFi está habilitado en el dispositivo
      • Conectado a la red correcta
      • Señal adecuada (>-70 dBm)
      • Contraseña correcta
    3. Verificar adaptador de red:
      • Adaptador habilitado en Windows/Linux
      • Drivers instalados y actualizados
      • No hay signos de ! amarillo en Device Manager
    4. Soluciones comunes:
      • Deshabilitar y re-habilitar adaptador
      • Reiniciar el dispositivo
      • Actualizar drivers
      • Verificar que no esté en "modo avión"

    Problema 2: "Conectado Pero Sin Internet"

    Síntomas: Conectado a red, pero navegador no carga páginas

    Diagnóstico sistemático:

    1. Verificar configuración IP:
      # Windows
      ipconfig /all

      # Verificar:
      • ¿Tiene dirección IP válida? (no 169.254.x.x)
      • ¿Máscara de subred correcta?
      • ¿Gateway configurado?
      • ¿DNS configurado?
    2. Probar conectividad local:
      ping 192.168.1.1 # Gateway típico
      # Si falla → problema con gateway o red local
      # Si funciona → continuar
    3. Probar conectividad Internet (por IP):
      ping 8.8.8.8 # Google DNS
      # Si falla → problema con router/ISP
      # Si funciona → problema es DNS
    4. Probar DNS:
      nslookup google.com
      # Si falla → problema de DNS
      # Si funciona → problema en navegador/firewall

    Soluciones según diagnóstico:

    • Si no tiene IP válida (169.254.x.x = APIPA):
      ipconfig /release
      ipconfig /renew
      • Si no obtiene IP → problema con DHCP server
      • Verificar que llega al servidor DHCP
      • Probar configuración estática temporal
    • Si problema es DNS:
      # Limpiar caché DNS
      ipconfig /flushdns

      # Configurar DNS público manualmente
      # En propiedades de adaptador:
      DNS Preferido: 8.8.8.8
      DNS Alternativo: 8.8.4.4
    • Si problema es navegador:
      • Limpiar caché del navegador
      • Probar en modo incógnito
      • Deshabilitar extensiones
      • Probar con otro navegador

    Problema 3: "Conexión Muy Lenta"

    Síntomas: Páginas tardan mucho en cargar, descargas lentas

    Diagnóstico:

    1. Aislar el problema:
      • ¿Afecta solo a este dispositivo? → problema local
      • ¿Afecta a todos? → problema de red/ISP
      • ¿Solo en WiFi? → problema de señal WiFi
      • ¿Solo en ciertas horas? → problema de congestión
    2. Verificar velocidad:
      • Usar speedtest.net
      • Comparar con velocidad contratada
      • Probar con cable vs WiFi
    3. Revisar uso de recursos:
      • Abrir Task Manager / Activity Monitor
      • Verificar procesos que consumen red
      • Buscar malware / programas no deseados

    Soluciones comunes:

    • Cerrar aplicaciones que consumen mucho ancho de banda
    • Si es WiFi: acercarse al AP, cambiar de banda (2.4→5GHz)
    • Escanear y eliminar malware
    • Actualizar drivers de NIC
    • Verificar duplex settings (auto/auto)

    Problema 4: "No Puedo Acceder a Recurso Compartido"

    Síntomas: "No se puede encontrar \\servidor\carpeta"

    Pasos de troubleshooting:

    1. Verificar conectividad al servidor:
      ping servidor
      ping 192.168.20.10 # IP del servidor

      # Si falla → problema de red/routing
      # Si funciona → problema de permisos/servicios
    2. Verificar resolución de nombres:
      nslookup servidor
      # Debe resolver a la IP correcta
    3. Verificar que el servicio esté corriendo:
      • SMB/CIFS debe estar habilitado
      • Firewall permite tráfico (puertos 139, 445)
    4. Verificar permisos:
      • Usuario tiene permisos en la carpeta compartida
      • Usuario está en el grupo correcto de AD
      • No hay "Deny" explícito
    5. Verificar credenciales:
      • Probar acceder con credenciales explícitas
      • Verificar que la contraseña no haya expirado

    Soluciones:

    • Limpiar credenciales guardadas: net use /delete \\servidor
    • Mapear unidad de red nuevamente
    • Verificar/corregir permisos en el servidor
    • Reiniciar servicio de "Workstation" en el cliente

    Checklist de Troubleshooting de Dispositivo Final

  • ¿El cable/WiFi está conectado?
  • ¿El adaptador de red está habilitado?
  • ¿Tiene dirección IP válida?
  • ¿Puede hacer ping al gateway?
  • ¿Puede hacer ping a Internet (8.8.8.8)?
  • ¿DNS funciona correctamente?
  • ¿Firewall local bloqueando tráfico?
  • ¿Drivers de NIC actualizados?
  • ¿Problema solo en este dispositivo o afecta a otros?
  • ¿Cambió algo recientemente (actualizaciones, nuevo software)?

    • 12.1.5 Solucionar Problemas de una Red

    Cuando el problema afecta a múltiples usuarios o toda la red, el enfoque debe ser más amplio y sistemático.

    Problemas de Red a Nivel Infraestructura

    Problema 1: "Toda la Red/Sitio Sin Conectividad"

    Impacto: Crítico - todos los usuarios afectados

    Enfoque de troubleshooting:

    1. Verificar dispositivos core:
      • ¿Router principal está up?
      • ¿Core switch está up?
      • ¿Módem/conexión WAN activa?
      • Revisar LEDs, logs del sistema
    2. Verificar alimentación:
      • ¿Hay energía en el rack/cuarto de equipos?
      • ¿UPS funcionando?
      • ¿Cables de poder conectados?
    3. Verificar enlace WAN:
      • ¿LED de Internet encendido en módem?
      • ¿Router tiene IP pública?
      • Contactar ISP si es necesario
    4. Revisar configuración:
      • ¿Cambios recientes en configuración?
      • ¿Actualización de firmware fallida?
      • Comparar con backup de configuración

    Acciones típicas:

    • Reiniciar dispositivos en orden: Módem → Router → Core Switch
    • Restaurar última configuración funcional conocida
    • Activar procedimiento de disaster recovery si necesario
    • Comunicar a usuarios estimación de tiempo de resolución

    Problema 2: "Piso/Departamento Sin Conectividad"

    Impacto: Alto - grupo de usuarios afectados

    Enfoque:

    1. Identificar el switch de distribución:
      • ¿Qué switch da servicio a ese piso/área?
      • Revisar diagrama de red
    2. Verificar el switch:
      # Conectar al switch (consola o SSH)
      show interface status
      show logging
      show spanning-tree
      show ip interface brief
    3. Buscar problemas comunes:
      • Uplink caído (conexión al core)
      • STP blocking todos los puertos
      • VLAN mal configurada
      • Trunking roto

    Problema 3: "Red Lenta para Todos"

    Impacto: Alto - degradación de servicio

    Diagnóstico:

    1. Identificar el cuello de botella:
      • Revisar uso de ancho de banda en enlaces clave
      • Monitorear CPU de routers/switches
      • Revisar utilización de puertos
    2. Buscar broadcast storms:
      show interface counters errors
      # Buscar alto número de broadcasts/multicasts
    3. Identificar tráfico anómalo:
      • Usar herramientas de monitoreo (PRTG, SolarWinds)
      • NetFlow / sFlow para análisis de tráfico
      • Buscar dispositivos haciendo escaneos, malware
    4. Revisar configuración de QoS:
      • ¿QoS configurado apropiadamente?
      • ¿Prioridad correcta para aplicaciones críticas?

    Soluciones:

    • Limitar/bloquear dispositivo causando tráfico excesivo
    • Implementar/ajustar QoS
    • Actualizar enlaces con mayor capacidad
    • Agregar más ancho de banda con ISP

    Uso de Herramientas de Monitoreo

    El monitoreo proactivo ayuda a identificar problemas antes de que afecten a usuarios:

    Herramientas comunes:

    • PRTG Network Monitor: Monitoreo de ancho de banda, sensores
    • SolarWinds NPM: Monitoreo completo de red, NetFlow
    • Nagios / Icinga: Open source, monitoreo de servicios
    • Zabbix: Open source, altamente escalable
    • LibreNMS: Open source, auto-discovery
    • Wireshark: Captura y análisis de paquetes

    Métricas clave a monitorear:

    • Uso de CPU/memoria en dispositivos de red
    • Utilización de ancho de banda por enlace
    • Latencia y packet loss
    • Estado de interfaces (up/down)
    • Errores en interfaces
    • Temperatura de equipos
    • Uso de energía (si hay PoE)

    12.1.6 Solucionar Problemas de Conectividad de Forma Remota

    La capacidad de solucionar problemas remotamente es esencial, especialmente con el aumento del trabajo remoto y sitios distribuidos.

    Herramientas de Acceso Remoto

    1. Acceso Remoto a Dispositivos de Usuario

    Herramienta Tipo Ventajas Consideraciones
    TeamViewer Comercial Fácil, atraviesa NAT, muy popular Costo para uso comercial
    AnyDesk Comercial/Free Rápido, ligero Menos features que TeamViewer
    Windows RDP Built-in Windows Nativo, seguro, sin software extra Requiere configuración de red/firewall
    Chrome Remote Desktop Gratis Gratis, cross-platform Requiere cuenta Google
    VNC Open Source Gratis, multi-plataforma Configuración más compleja

    2. Acceso Remoto a Dispositivos de Red

    • SSH (Secure Shell):
      • Protocolo estándar para acceso remoto
      • Cifrado, seguro
      • Puerto TCP 22
      • Herramientas: PuTTY, SecureCRT, terminal nativo
    • Console Server:
      • Dispositivo dedicado con múltiples puertos de consola
      • Acceso out-of-band a dispositivos
      • Útil cuando SSH no funciona
    • Management VLANs:
      • VLAN dedicada para gestión
      • Aislada del tráfico de usuarios
      • Acceso controlado

    Proceso de Soporte Remoto Efectivo

    1. Preparación:
      • Recopilar información del usuario antes de conectar
      • Asegurar que tienes las credenciales necesarias
      • Verificar que tienes conectividad al dispositivo
    2. Establecer conexión:
      • Guiar al usuario para aceptar conexión (si es necesario)
      • Pedir permiso antes de tomar control
      • Explicar que verás su pantalla
    3. Durante la sesión:
      • Narrar lo que estás haciendo
      • Pedir al usuario que cierre documentos sensibles
      • No curiosear archivos del usuario
      • Mantener comunicación constante
    4. Documentar:
      • Capturar screenshots de errores
      • Anotar configuraciones encontradas
      • Documentar pasos de resolución
    5. Verificación:
      • Confirmar que el problema está resuelto
      • Hacer que el usuario pruebe
      • Explicar qué se hizo y por qué
    6. Cierre:
      • Cerrar la sesión remota apropiadamente
      • Agradecer al usuario
      • Actualizar el ticket
    Mejores Prácticas de Soporte Remoto:

    1. Seguridad primero
    • Usar conexiones cifradas (SSH, VPN)
    • Autenticación fuerte (no contraseñas débiles)
    • Registrar todas las sesiones remotas
    • Cerrar sesión inmediatamente después de terminar

    2. Comunicación clara
    • Explicar qué harás antes de hacerlo
    • Mantener al usuario informado del progreso
    • Usar lenguaje no técnico con usuarios finales

    3. Respeto a la privacidad
    • No abrir archivos personales
    • Pedir permiso antes de acceder a áreas sensibles
    • Minimizar ventanas con información privada

    4. Documentación completa
    • Capturar evidencia de errores
    • Documentar estado antes y después
    • Registrar configuraciones modificadas

    5. Eficiencia
    • Tener herramientas listas antes de conectar
    • Usar scripts para tareas repetitivas
    • Minimizar tiempo de conexión (es invasivo para el usuario)
    Desafíos del Soporte Remoto:

    • Latencia: Conexión lenta dificulta el trabajo
    • Falta de visibilidad física: No puedes ver cables, LEDs
    • Dependencia del usuario: Usuario debe estar disponible
    • Problemas de conectividad: Si la red no funciona, no puedes conectar
    • Zona horaria: Usuarios en diferentes husos horarios

    Mitigaciones:
    • Tener acceso out-of-band (console servers, LTE backup)
    • Capacitar usuarios básicos en troubleshooting físico
    • Mantener documentación actualizada y accesible
    • Implementar monitoreo proactivo para detectar problemas antes
    • Considerar personal on-site para sitios críticos

    Puntos Clave de la Clase 12

    • Soporte de red requiere metodología estructurada: Bottom-Up, Top-Down, Divide and Conquer
    • Documentación es crítica: diagramas, inventario, configuraciones, procedimientos
    • Help Desk usa modelo de niveles: Tier 1 (básico), Tier 2 (técnico), Tier 3 (expertos)
    • Sistema de ticketing organiza solicitudes con prioridades y SLAs
    • FCR (First Contact Resolution) es métrica clave de efectividad del help desk
    • Documentar cada paso de troubleshooting - "si no está documentado, no pasó"
    • Usar ping progresivo: gateway → IP pública → dominio para diagnosticar
    • Problemas de dispositivos finales: verificar físico → IP → gateway → DNS
    • Problemas de red completa requieren verificar core devices primero
    • Monitoreo proactivo identifica problemas antes de que afecten usuarios
    • Soporte remoto requiere herramientas adecuadas y respeto a privacidad del usuario
    • Comunicación efectiva es tan importante como habilidades técnicas
